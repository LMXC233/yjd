这个 demo 回答一个问题：按 ADR-0007（纯 Redis 会话，不用 JWT）定稿的运营登录——滑动续期、单设备互踢、封号全踢、登出即死、Redis fail-close、限流锁定——按真实操作序列跑起来之后，行为是否和你的预期一致？ 左侧是完整状态（每次点击后刷新），右侧上半是自由操作，下半是引导场景。demo 建模了两个浏览器（运营在两台设备上登录的场景），可以切换视角观察「踢单设备」。时间是被虚拟化的：用「时间快进」推着 4 小时滑动 TTL、10 分钟失败窗口、30 分钟锁走完它们的一生。
✅ 语义定稿记录（2026-09-29 拍板；demo 按此实现）
  1. 登录成功 → 失败计数清零。
  2. 失败窗口 = 滑动窗口：只统计最近 10 分钟内的失败。
  3. 锁到期自动解除、从零重新计数；锁定期内继续尝试不重置计时、不计数。
  4. 踢单设备 = 登录时自动踢旧会话，同一账号全局只允许一个活跃会话（运营手动踢人归后期员工管理）。
  5. 续期时机 = 每次校验通过即续满 4 小时（含 GET /me 读请求）。
  6. UA·IP 摘要仅作记录，暂不参与校验。
  7. 封号 = DB 层禁用 + 扫反向索引全踢（Redis 无 token 可验、MySQL 无法登录）；主动封号的操作界面（HRM）后期再做；会话校验路径不查 DB 账号状态。
  8. 登录失败分层提示：第 1~4 次失败与禁用账号统一 401「手机号或密码错误」（防枚举主战场）；锁触发与锁定期返回 401 + code=ACCOUNT_LOCKED + retryAfter（秒），前端展示「已临时锁定，请 X 分钟后再试」；锁计数按手机号维度、不存在的手机号同样计数上锁——锁定提示对存在/不存在的手机号表现完全一致，零枚举价值（见场景 H）。
